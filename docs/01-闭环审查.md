# 闭环审查与 v6 修正

## 结论
原构想的方向成立：识别归档 → 约束 → 执行判断 → 方案与输出 → 反馈。
缺口不在步骤数量，而在“允许修改什么、哪个版本获批、出了错回到哪里、怎样证明正确”。

| 原缺口 | 风险 | v6 处理 |
|---|---|---|
| v5 把红线扩成数据、版式永久不可改 | 优化无法发生；也不符合本轮对运行边界的澄清 | 原件不可覆盖；文本结构/图片/已确认分析默认保护，修改走精确审批。发现数据错误只提修订，不静默纠错 |
| 第一步/第二步与“阶段2”混称 | 自动起草与人工确认相互矛盾 | 用状态名替代序号：识别/标签/约束草案自动；确认是门控事件，不是一整个手工阶段 |
| 无输入质量门槛 | OCR 错字被带入分析 | 对照页数、提取覆盖、扫描页、图表数据和实际片段；未提取不得当作无内容 |
| Architect OS 产物与核验职责未隔离 | 纪要看似成品就被当成证据 | 只读接收纪要及内容哈希；数据事实进入 claims ledger，不修改上游工作流 |
| 重大问题没有分级 | 无限回约束层，浪费人工 | P0 停止发布并局部回退；P1 返回对应产物；P2 自动修复非保护格式。回退表和失效规则明确 |
| 先正式生成再选方案/做大纲 | 返工和重复生成 | 先核验证据、再方案，选定后先大纲/页框架，再物料、渲染；⑤⑥⑦保留为产物类型而非强制倒序 |
| 一页一图被当成每页必须图表 | 目录页、流程页被强塞图表 | 改为每页一个核心信息任务；证据页优先一个主图，辅助图须语义相关；封面/目录/结论可无图 |
| 汇报与打印只靠字号切换 | 打印缩水、事实版本漂移 | 共用 content model 的 claim_id，分别选择版式。打印可增加解释，不可改事实口径 |
| 落盘等于上下文不占用 | 全量规则与历史仍被塞进对话 | 常驻短规则+有限索引+分片读取；无法强制释放已进入的内容，必要时用恢复包开新会话 |
| 只说人工确认 | “确认”审批错版本 | 审批绑定运行、门控、目标路径、目标哈希、范围、有效状态；变更后旧审批失效 |
| 10分钟防卡死不可实际计时 | Agent 陷入自循环 | 失败次数上限+输入输出哈希无进展检测；10分钟只在有可用墙钟时辅助触发 |
| 联网缺少可信边界 | 找到好看网站就当事实源 | 参考站点分 purpose；先优选站，再受控扩域；记录准确 URL、访问日、版本和支持的主张 |
| 最终只检查“文件存在” | 内容丢失、乱码、导出失败 | 结构/数字/视觉/跨版一致性/审批/交付哈希六类验收；缺视觉能力不能声称视觉通过 |
| 反思直接改工作流 | 一次偶然结果污染永久规则 | 运行反馈 → 变更提案 → 人工同意 → 新版本 → 回归测试；失败可恢复上一版 |

## 运行闭环
RECEIVED → IDENTIFIED → TAGGED → CONSTRAINTS_DRAFTED → CONTRACT_APPROVED
→ VERIFIED → OPTIONS_READY → OPTION_APPROVED → CONTENT_READY → CONTENT_APPROVED
→ RENDERED → QA_PASSED → RELEASE_APPROVED → RELEASED → RETROSPECTED。

默认三个批量人工门：契约、内容/方案、发布。为减少打断，OPTION_APPROVED 可与后续内容审批在同一轮用户交互中预审，但不能审批尚不存在的页框架；脚本仍分别留痕。
额外门仅在结构重排、图片替换、既有分析变更、数据修订、重新设计原有版式等保护范围触发。

## 不夸大的保证
Schema 能查字段，不会判断事实真假；哈希能查版本，不会证明内容正确；提示词能约束行为，不是访问控制。
只有外部宿主实际执行工具门禁、只读目录和审批授权，才能实现强制隔离。本包先提供可审计、可接入的接口。
